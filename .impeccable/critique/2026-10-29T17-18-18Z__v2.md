## Design Specificity Verdict

**LLM assessment:** authored for this product. The Flight Recorder idea holds throughout: mono timestamps in fixed columns, badges with their host or tracker marks, progress steps coded by shape, lavender kept to needs-you. The one generic screen left is Ask's new-chat page. The weak spots are now copy where machine vocabulary leaks through ("max_turns", "Built … (attempt n)"), not the visual language.

**Deterministic scan:** the source trees and the snapshots are clean. B found three things the scan misses, all P3: the 10px rail nav count (`shell.css:515`, aria-hidden, so the detector skips it), cards inside cards when a phone `DataTable` sits in a `Card`, and several 11px labels.

**Visual overlays:** none. There is no browser automation on the host.

## Overall Impression

Round 2's polish list was cleared without regressions, and every automated accessibility and Decided check is clean across the full matrix. The one real problem is the desktop Ask panel, which has never shown its chats; earlier rounds misread it as capture timing, and TOOL-825's `waitFor` exposed it.

## What's Working

1. **Truthful failure states.** A failed run never shows a ✓ turn, and the error flows from run to step to Activity.
2. **Consistency.** One retry glyph built once in `@omniralph/ui`, kind·state labels on Runs and Inbox, labeled add buttons on every repo card, and back links above titles.
3. **Complete flows.** Add repos (filter, Private and Added badges, one recovery control), and the agent Version page explains why it runs the version it does.

## Priority Issues

- **[P1] The desktop Ask panel never shows its chats** (newly noticed; present since round 1).
  - What: `ask-panel.{desktop,rail}.{dark,light}.png` show the panel opened over `/runs` stuck on the "Loading chats" skeleton. The route's `waitFor` times out in all 4 captures, in three consecutive runs (`15-51-49`, `16-23-43`, `17-06-23`). Round 2's and earlier captures (no `waitFor` then) show the same skeleton: `2026-10-29T13-42-40-688Z/ask-panel.desktop.dark.html` still contains "Loading chats". `ask.desktop.light` lists 5 chats through the same `AskChatsList`/`useAskChats` (`apps/web/src/components/ask/ask-chats-list.tsx:150`, `use-ask-chats.ts:33-48`), so the API and data work; the fault is in the panel's mount beside a page (`ask-panel.tsx`, `app-shell.tsx:158`). No console error is logged. No query-key collision was found statically.
  - Why: above 768 px the Ask entry and its shortcut only toggle the panel (`withAskEntry`), so desktop and rail users have no in-app way back to an earlier chat. The skeleton never becomes an error (the error branch needs `list.isError`), so the region stays busy forever with no Retry.
  - Fix: reproduce in a browser (`/runs` → Ask) and watch `/api/ui/ask/chats` (never sent, pending, or aborted and re-issued — e.g. the infinite query cancelled by invalidations from the fixture's running Ask runs, or its observer remounting). Fix the cause, keep the route's `waitFor`, and add a test that the panel's list loads.
  - Serves: rule 22, H1, H9, WCAG 4.1.3. Suggested: /impeccable harden.
